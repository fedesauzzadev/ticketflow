# Backlog — TicketFlow

**Formato AC:** Given/When/Then observables. Cada historia verifica con evidencia real (comando + resultado esperado). El "cómo técnico" (patrones, librerías, servicio AWS concreto) lo decide el Tech Lead en Fase 2.

| ID | Historia | Criterios de aceptación observables | Valor | Tamaño |
|----|----------|-------------------------------------|-------|--------|
| H-01 | **Como evaluador quiero** consultar eventos y su disponibilidad **para** ver el catálogo y comprobar cache en el path intensivo de lectura. | **AC1** Given un evento con N entradas, When `GET /events/{id}/availability` dos veces, Then la 1ª responde `X-Cache: MISS` y la 2ª `X-Cache: HIT`, ambas con la misma disponibilidad correcta.<br>**AC2** Given disponibilidad ya cacheada, When se completa una compra de ese evento, Then `GET /events/{id}/availability` devuelve el valor actualizado (invalidación; no el cacheado).<br>**AC3** Given seed inicial, When `GET /events`, Then lista ≥2 eventos con nombre, fecha, precio y disponibilidad.<br>**AC4** Given datos creados vía API, When se reinician los microservicios (no el emulador), Then `GET /events` sigue devolviendo los datos ⇒ el estado vive en el emulador :9297. | Alto | M |
| H-02 | **Como comprador (vía curl) quiero** comprar una entrada con pago aprobado o rechazado **para** ver la saga orquestada completa con compensación. | **AC1** Given evento con disponibilidad, When `POST /purchases` con `Idempotency-Key: K1` y PAN aprobado, Then responde 201 con `purchase_id` y `GET /purchases/{id}` evoluciona a estado terminal `TICKETS_ISSUED` con su ticket emitido (id/QR referenciable).<br>**AC2** Given compra exitosa de 1 asiento, When `GET /events/{id}/availability`, Then la disponibilidad decrece exactamente 1.<br>**AC3** Given PAN de rechazo (termina `0002`), When `POST /purchases`, Then la compra termina `FAILED` con motivo visible y la disponibilidad vuelve al valor previo (asiento liberado — compensación observable).<br>**AC4** Given saga en curso o terminada, When `GET /purchases/{id}`, Then expone su estado (`PENDING`/`SEATS_RESERVED`/`PAYMENT_APPROVED`/`TICKETS_ISSUED`/`FAILED`) — estado compartido entre servicios observable por API. | Alto | L |
| H-03 | **Como evaluador quiero** repetir la compra y duplicar comandos **para** comprobar que la idempotencia no duplica efectos de negocio. | **AC1** Given compra exitosa con key `K1`, When `POST /purchases` repetido con la misma `K1` y mismo cuerpo, Then devuelve la misma compra (mismo `purchase_id`) y ni la disponibilidad ni los tickets emitidos cambian respecto de una sola ejecución.<br>**AC2** Given un comando interno duplicado (p.ej. reserve-seats encolado 2 veces con igual correlación), When el worker lo procesa, Then la disponibilidad decrece una sola vez y el log muestra duplicado detectado/descartado.<br>**AC3** Given key distinta `K2` pidiendo asientos ya reservados/agotados, When `POST /purchases` con `K2`, Then falla explícitamente (409/422) con motivo, sin efectos parciales silenciosos. | Alto | M |
| H-04 | **Como reclutador quiero** README + scripts de demo **para** levantar el proyecto yo mismo y ver las evidencias sin leer código. | **AC1** Given repo clonado y Docker, When sigo el quickstart del README, Then un comando documentado levanta emulador + 4 servicios y el flujo consulta→compra→ticket funciona.<br>**AC2** When ejecuto `demo-idempotency` (script), Then imprime: misma key ⇒ misma compra; disponibilidad idéntica antes/después del replay.<br>**AC3** When ejecuto `demo-cache` (script), Then imprime `MISS` → `HIT` → invalidación con valores.<br>**AC4** Given el repositorio, When leo el README, Then encuentro diagrama de arquitectura, decisión de dominio (link a ADR), quickstart y mapa de patrones aplicados (patrón → dónde vive). | Alto | M |

=== CORTE MVP ===

**Por qué este corte:** H-01..H-04 = catálogo+cache, saga completa, idempotencia y documentación ejecutable. Es vendible por sí solo: un evaluador ve los cuatro pilares del requerimiento (orquestación, idempotencia, cache, AWS local) con evidencia imprimible por scripts. Todo lo demás es ampliación (ver roadmap.md).
