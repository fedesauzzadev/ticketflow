Caso de estudio · backend distribuido sobre AWS

Vender entradas sin vender dos veces el mismo asiento.

TicketFlow es un backend de venta de entradas para eventos de alta demanda: 4 microservicios .NET 10 coordinados por una saga, sobre DynamoDB, SQS FIFO, S3, Lambda, Cognito, Parameter Store, Bedrock y EKS, con la infraestructura en Terraform y los servicios en Docker y Kubernetes. Corre completo en una laptop contra el emulador local de AWS, sin cuenta ni costo.

Sistemas distribuidos

Arquitectura

Los servicios no se llaman entre sí para avanzar una compra: se pasan comandos y eventos por colas SQS FIFO. Órdenes es el orquestador y el único que conoce el estado de la saga.

Los cuatro servicios usan SQS y DynamoDB; solo Ticketing escribe en S3 y solo Catálogo llama a Bedrock. Los servicios corren como procesos locales, como contenedores Docker o como pods en un cluster Kubernetes local, siempre en los mismos puertos. El cluster EKS del emulador es solo control plane: está declarado y activo, pero no ejecuta contenedores.

Decisiones de ingeniería

Cada una tiene su registro en brain/decisions/, con el contexto y las alternativas descartadas. Estas son las que más cambiaron el diseño.

Un manifiesto, dos ejecutoresTerraform y la herramienta .NET leen la misma lista de recursos

Problema. Los nombres de tablas y colas vivían en constantes del código, en un manifiesto JSON y, al sumar Terraform, iban a vivir en un tercer lugar.

Decisión. El HCL no lista recursos: hace for_each sobre jsondecode(file("aws-local.json")). Un test compara ese manifiesto contra las constantes del código y falla si alguno cambia sin el otro.

Descartado. Escribir los 15 recursos a mano en HCL. Es lo habitual, pero duplica la lista y pide un segundo test de deriva.

Saga por orquestaciónUn servicio conoce el flujo; los demás solo ejecutan pasos

Problema. Reservar, cobrar y emitir tocan tres servicios y cualquiera puede fallar a mitad de camino.

Decisión. Órdenes es el orquestador: guarda el estado de cada compra y decide el paso siguiente o la compensación. Los mensajes salen por un outbox para no perder ninguno si el servicio se cae entre guardar y publicar.

Descartado. Coreografía por eventos. Con cuatro servicios, el flujo quedaba repartido y era difícil responder «¿en qué estado está esta compra?».

Lambda disparada por S3, no invocada por el servicioAgregar la notificación no tocó una línea de .NET

Problema. La notificación de «entradas emitidas» era un log interno, porque el fan-out de SNS no entrega mensajes en el emulador.

Decisión. Ticketing ya guardaba un QR por entrada en S3. Una notificación del bucket dispara la Lambda. El servicio no sabe que la función existe.

Descartado. Invocar la Lambda desde el servicio (acopla el camino crítico a la notificación) y una cola SQS nueva (obligaba a tocar el servicio y el manifiesto compartido).

Dos barreras contra llamar a AWS realY cómo se abrió una, con cuidado, para los contenedores

Problema. Un error de configuración no debe terminar en una llamada firmada contra AWS de verdad. Pero dentro de un contenedor el emulador deja de ser localhost, y la regla original rechazaba cualquier otro host.

Decisión. Se mantiene la barrera dura: el cliente HTTP solo acepta una cadena TLS cuya raíz sea la autoridad certificadora del emulador. La barrera de host admite un único nombre extra, por variable de entorno, con coincidencia exacta y nunca un dominio de AWS. Sin la variable, todo se comporta como antes. 17 casos de test.

Descartado. Quitar la validación de host y confiar solo en el certificado: pierde una capa y el mensaje de error claro al arrancar.

Un Dockerfile para cuatro serviciosMismo proceso de build, cuatro imágenes

Decisión. Un Dockerfile multi-stage con un argumento de build elige el servicio. La imagen final lleva solo el runtime, corre como usuario sin privilegios y no contiene credenciales: entran por variables de entorno y el certificado se monta como volumen de solo lectura.

Costo aceptado. Cualquier cambio en el código vuelve a restaurar dependencias. Está marcado en el archivo como atajo a revisar si el build empieza a ser lento.

Kubernetes local en lugar del EKS del emuladorDecidido después de probarlo, no antes

Problema. El emulador crea el cluster EKS y hasta expone una API de Kubernetes con los nodos registrados.

Lo que se probó. Un pod de prueba fue aceptado y asignado a un nodo, pero terminó en Failed: no hay un runtime de contenedores detrás.

Decisión. EKS queda declarado en Terraform para la parte de AWS (red, IAM, grupo de nodos). Los manifiestos, que son Kubernetes estándar, se despliegan en un cluster local. En EKS real cambiarían el origen de las imágenes y el tipo de Service.

Bugs reales encontrados en el camino

Ninguno apareció leyendo código. Todos salieron de ejecutar el sistema, y cada uno dejó un test, una corrección en la causa o una regla documentada.

SDK

El cliente hablaba con AWS real en silencio

Síntoma: errores TLS inexplicables contra el emulador.

Causa: en el SDK v4, configurar región y URL a la vez hace que gane la región, y el tráfico sale al endpoint real.

Corrección: URL más región de autenticación, y certificado pineado para que no pueda repetirse.

S3

Ticketing no arrancaba en contenedores

Síntoma: Name or service not known (ticketflow-tickets.host…).

Causa: con el endpoint por IP el SDK usaba rutas tipo host/bucket; con un nombre de host pasa a bucket.host, que no existe.

Corrección: forzar el estilo de ruta en el cliente S3 y volver a correr la suite completa.

Mensajería

Una compra quedaba colgada para siempre

Síntoma: con dos fallos encadenados la compra nunca llegaba a un estado final.

Causa: dos mensajes de fallo distintos compartían identificador de deduplicación y SQS FIFO descartaba el segundo sin avisar.

Corrección: el paso fallado entra en el identificador. Tres tests que fallan sin el arreglo.

Bedrock

Unas respuestas colgadas frenaban el servicio

Síntoma: con 20 a 40 respuestas que no terminaban de llegar, el servicio se quedaba sin hilos.

Causa: el SDK lee el cuerpo de la respuesta de forma síncrona y su timeout no cubre esa lectura.

Corrección: el cuerpo se descarga de forma asíncrona y cancelable antes de entregarlo al SDK. Con test.

Lambda

Una clave nula tiraba la función

Síntoma: excepción en el test de entradas hostiles, antes de desplegar.

Causa: un evento con la clave del objeto en null llegaba hasta el decodificador de URL.

Corrección: el evento malformado se ignora y se registra. Terraform redesplegó solo esa función.

IAM

El disparador desde SQS era rechazado

Síntoma: error al asociar una cola a la Lambda.

Causa: el rol de ejecución no tenía permiso para leer de la cola. El emulador valida IAM igual que AWS.

Corrección: con la policy correcta funcionó, también con colas FIFO. Quedó documentado como material de estudio.

Scripts

El arranque fallaba tras reiniciar Docker

Síntoma: el chequeo de salud del emulador fallaba por certificado.

Causa: una carrera: el script copiaba el certificado viejo antes de que el emulador generara el nuevo.

Corrección: volver a copiarlo mientras el chequeo falle. Reproducido reiniciando el contenedor a propósito.

Cómo se verifica cada entrega

  • Criterios antes del código. Cada entrega tiene criterios de aceptación observables, escritos antes de empezar.
  • Un comando para todo. scripts/ci.ps1 corre build sin warnings, tests, cobertura y verificación de infraestructura, e informa qué etapa falló.
  • El mismo script en la nube. GitHub Actions invoca ese script, sin lógica propia.
  • Revisión adversarial. Las tres primeras versiones pasaron una ronda que intenta refutar cada criterio: datos hostiles, carreras, fallos dobles.
  • Evidencia guardada. Cada verificación deja comando y resultado en brain/evidence/.

Además: 4 tests del handler de la Lambda en Python, fuera de la suite .NET.

Límites, dichos sin vueltas

Esto es un emulador en una laptop. Saber dónde termina lo que se probó es parte del trabajo.

Del emulador
  • EKS no ejecuta pods. Es plano de control; los servicios corren en un cluster local.
  • SNS no entrega mensajes. El fan-out a colas falla; la notificación se resolvió con S3 y Lambda.
  • Bedrock no ejecuta modelos. Devuelve un texto fijo.
  • El estado vive en memoria. Reiniciar el contenedor borra todo; Terraform lo recrea.
  • Se satura con arranques simultáneos. Reiniciar los 4 servicios a la vez puede hacer que alguno falle su primer intento; Kubernetes lo relanza.
Del proyecto
  • Nunca corrió contra AWS real. Latencias, límites de servicio y costos reales no están medidos.
  • Una réplica por servicio. Escalar horizontalmente los consumidores de la saga no está verificado.
  • El CI no ejecuta Terraform, Docker ni Kubernetes. Esas partes están verificadas en local, con evidencia guardada.
  • El mínimo privilegio de la Lambda se revisó leyendo la configuración. No se probó que una invocación sin permiso sea rechazada.
  • Autenticación solo en Órdenes. Pagos, Ticketing, el asistente de eventos y los endpoints de administración siguen abiertos; el asistente tampoco limita peticiones. No hay pasarela de pago real.

Correrlo en tu máquina

Requisitos: Docker Desktop y el SDK de .NET 10 en Windows con PowerShell. Para los pasos de Terraform y Kubernetes: terraform, kind, kubectl y aws.

# 1. Infraestructura (levanta el emulador si hace falta)
powershell -ExecutionPolicy Bypass -File scripts\terraform.ps1 apply

# 2. Servicios: elegir UNA de las tres formas (usan los mismos puertos)
powershell -ExecutionPolicy Bypass -File scripts\run-local.ps1     # procesos .NET
powershell -ExecutionPolicy Bypass -File scripts\run-docker.ps1    # contenedores
powershell -ExecutionPolicy Bypass -File scripts\run-k8s.ps1       # Kubernetes (kind)

# 3. Demos con salida verificable (exit 0 = todo pasó)
powershell -ExecutionPolicy Bypass -File scripts\demo-idempotency.ps1
